# WP1 Results — SWE-bench Verified, 100 instances (2026-10-28)

Pre-registration: `PREREG_WP1_SWEBENCH_VERIFIED_DRAFT.md`, frozen at
`ad4964e`, with Amendment 1 (output cap) and Amendment 2 (arm R's provider
failures retried). Pilot: `WP1_PILOT_2026-10-28.md`.

**In short.**

- The Agent resolved 64% and 59% of 100 SWE-bench Verified instances
  across its two seeds, and 52% in both.
- mini-SWE-agent with the same model resolved 70%.
- The pre-registered paired comparison found no significant difference
  between the Agent (seed 101) and mini-SWE-agent: −6 pp, exact McNemar
  p = 0.24. The point estimate favors mini-SWE-agent.
- The Agent does not outperform a minimal public agent on this model. In
  an exploratory, post-hoc look, most of the instances that only
  mini-SWE-agent resolved were runs the Agent's retry guard had stopped.

## Setup

As pre-registered (§2–§4); details in the pilot report.

- **Host.** WSL2 Ubuntu 24.04, x86_64, 24 CPUs, 31 GB, Docker Engine.
  Grading by the unmodified `swebench` 5.0.2 harness.
- **Sample.** 100 Verified instances, seed 20261028, drawn from the 490
  non-pilot instances.

  | Repository | Instances |
  |---|---|

- **Model.** Both arms used the same model and request settings: `glm-5.1`

  `max_tokens` 8192.
- **Arm A.** This Agent:
  - C3, `policy_mode=legacy`, 40 steps, 30-minute wall cap per instance;
  - `--network none`, 2 CPUs, 6 GB;
  - 2 workers, processing order seed 20261029;
  - model seeds 101 and 202.
- **Arm R.** mini-SWE-agent 2.4.6 with litellm 1.93.0, its default
  SWE-bench prompt, step limit 40, `--network none`, 2 workers.
- **Commits.**
  - A-s101: the first 25 instances ran at `ad4964e`, the other 75 at
    `1fb16fa`.
  - A-s202 and R's first attempt ran at `1fb16fa`.
  - R's retry ran at `b8dc635`.
  - Between these commits only the runner's `--stop-after`, the scripts,
    the summarizer and documents changed. The Agent loop, tools, prompts
    and `config.yaml` are identical.

## Primary result (pre-registered)

| Measure | Resolved | 95% Wilson |
|---|---|---|
| A, seed 101 | 64/100 | 54.2%–72.7% |
| A, seed 202 | 59/100 | 49.2%–68.1% |
| A, resolved in both seeds | 52/100 | 42.3%–61.5% |

The two seeds disagree on 19 instances: 12 resolved only with seed 101 and
7 only with seed 202 (McNemar p = 0.36). One run of 100 instances moves by
about 5 pp between seeds, which is why "resolved in both seeds" is
reported.

## Secondary results (pre-registered)

**A versus R.** Exact McNemar test, seed 101 against R:

| | Both | Only A | Only R | Neither | McNemar p | Difference (95% paired bootstrap) |
|---|---|---|---|---|---|---|
| A-s101 vs R | 58 | 6 | 12 | 24 | 0.24 | −6.0 pp (−14.0 to +2.0) |

R resolved 70/100 (60.4%–78.1%). The difference is not significant.
§5 said that n = 100 detects only differences of roughly 10–15 pp, so
this is a null result, not evidence of parity.

**Outcomes per arm.**

| Arm | Resolved | Unresolved | Empty patch | Infra | Provider | Harness | Wall cap |
|---|---|---|---|---|---|---|---|
| A-s101 | 64 | 31 | 5 | 0 | 0 | 0 | 0 |
| A-s202 | 59 | 34 | 7 | 0 | 0 | 0 | 0 |
| R | 70 | 21 | 9 | 0 | 0 | 0 | 0 |

- The harness marks some unresolved instances as "ambiguous"
  (`no_tests_collected`) and counts them as unresolved; so does this
  report:
  - A-s101: `pytest-10051`, `pytest-10356`, `pytest-5787`;
  - A-s202: `pylint-4604`, `pytest-10051`, `pytest-10356`;
  - R: `pylint-4604`, `pytest-10356`.

  `pytest-10356` is ambiguous in all three arms.
- R's 9 empty patches:
  - 8 runs reached the step limit (`LimitsExceeded`). mini-SWE-agent
    submits nothing in that case.
  - 1 ended with `RepeatedFormatError`, on `sympy-23413`. Arm A's only
    `loop_exception` in each seed was on the same instance: the model hit
    `max_tokens` with no text or tool call. That instance makes GLM
    produce degenerate output in both agents.
- R's first attempt scored 61/100 (51.2%–70.0%). 16 instances failed with
  `RateLimitError` before Amendment 2 (see "Deviations"). All 16 were
  submitted on retry, and 9 of them resolved.

## Exploratory analyses (not pre-registered)

These were chosen after seeing the results. They describe where the arms
differ. They do not test any hypothesis.

**A-s202 versus R.**

| | Both | Only A | Only R | Neither | McNemar p | Difference (95% paired bootstrap) |
|---|---|---|---|---|---|---|
| A-s202 vs R | 51 | 8 | 19 | 22 | 0.052 | −11.0 pp (−21.0 to −1.0) |

The bootstrap interval excludes 0, but the exact test does not reach 0.05,
and this is a second comparison of the same arms. The mean of the two
seeds is 61.5%, against 70% for R.

**Where R's lead comes from.** For each discordant instance, how arm A's
run ended:

| | Instances | Arm A's run ended by |
|---|---|---|
| Only R resolved, vs A-s101 | 12 | retry guard 11, `model_stop` 1 |
| Only R resolved, vs A-s202 | 19 | retry guard 16, `model_stop` 2, `max_steps` 1 |
| Only A-s101 resolved | 6 | `model_stop` 6 |
| Only A-s202 resolved | 8 | `model_stop` 3, retry guard 5 |

- Nearly all of R's extra resolves are instances where the Agent's retry
  guard stopped the run before a fix.
- The guard does not always cost a resolve: in 5 of A-s202's 8 wins, the
  patch left at the guard stop still resolved.
- This is consistent with the guard being the Agent's main deficit
  against R on this model, and it matches the pilot. It is not proof. A
  test would need its own pre-registered ablation (for example, the guard
  off, or reset after a successful step) on the same instances.

**Overlap.**

- All three arms resolved 47 instances, and none resolved 21.
- 71 were resolved by at least one arm-A seed. That is a best-of-two
  number and not comparable with a single run.

## Deviations from the pre-registration

1. **Amendment 1, output cap 1M → 2M.**
   - The §7 checkpoint stopped the run as designed: 1,055,916 output
     tokens projected against a 1M cap, with input within its cap.
   - The cap was raised before any formal instance was graded, together
     with a fix that stops `--stop-after` from running past the
     checkpoint on a rerun.
   - The projection turned out high: the whole run used 0.88M output
     tokens, below even the original cap. The first 25 instances of the
     processing order averaged 3,520 output tokens against 2,579 over all
     200 arm-A runs.
   - Projected input was 22.6M and actual input was 29.4M. The
     projection assumed arm R uses as much as arm A; it used about twice
     as much.
2. **Amendment 2, arm R's provider failures retried.**
   - From 18:45 to 19:32 EDT, 16 arm-R instances failed with z.ai 429
     code 1308, the Coding Plan's 5-hour quota, after both arm-A runs had
     finished.
   - Arm R's script had no retry step, and the summarizer showed 0
     provider errors for it because it read only the harness report.
   - Following §5 and §7, the 16 were retried once with identical
     settings, selected by exit status alone. The first attempt is kept
     (`*.attempt1.*`) and reported above.
   - This was decided after all arms were graded.
3. **A-s101 ran at two commits** (`ad4964e` for the first 25 instances,
   `1fb16fa` after Amendment 1). The runner rewrites `agent_commit` on
   resume, so its manifest names only `1fb16fa`. The Agent code is
   identical at both commits.
4. **§7 said mini-SWE-agent does not record tokens.** Its trajectories
   keep each call's usage, and R's tokens are reported from them.
5. **§8 output not yet produced:** the EvalOps `agent/v1` aggregate report
   per arm.
6. **Protocol differences between the arms**, which the pre-registration
   did not spell out:
   - At the step limit, arm A grades its working-tree diff and arm R
     submits nothing. No arm-A run that hit the limit resolved, so this
     did not change arm A's count. R's 8 step-limit runs could not
     resolve.
   - Arm A has a 30-minute wall cap per instance; arm R has none. No
     arm-A run came near it (the longest took 666 s).
   - Arm A streams its model calls, with a 120-second idle timeout. Arm R
     makes non-streaming calls without a timeout, which explains its long
     stalls. This affects wall time only, not outputs.
   - Arm A processes the sample in a seeded order. mini-SWE-agent runs it
     alphabetically, so the quota failures hit a contiguous block of
     repositories (matplotlib to pytest).

## What this supports

**Supported**, with the qualifiers above:

- On a fixed random 100-instance SWE-bench Verified subset, with official
  instance images and the unmodified harness, this Agent with GLM-5.1
  (thinking off) resolved 64% and 59% in two seeds (52% in both).
- mini-SWE-agent 2.4.6 resolved 70% under the same model, settings and
  step limit.
- The pre-registered comparison found no significant difference
  (−6 pp, McNemar p = 0.24).

**Not supported:**

- that the Agent is better than, or equal to, mini-SWE-agent;
- any claim about verification gates (§6: no gate arm);
- any claim for other models, or for GLM with thinking on;
- any leaderboard comparison: this is a 100-instance subset with a
  40-step limit.
